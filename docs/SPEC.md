# SPEC Tracking-Research-Status MVP
## Users
- MVP รอบนี้ให้ใช้งานในบทบาทผู้ดูแลระบบก่อน ยังไม่มี authentication/user accounts หรือการแยกสิทธิ์จริงของสามบทบาท; รายการบทบาทด้านล่างเป็นเป้าหมายภายหลัง
- ผู้ดูแลระบบ: เพิ่มงานวิจัย, ดูรายการงานวิจัยทั้งหมด, ลบงานวิจัย, แก้ไขข้อมูล
- ผู้ประสานงาน: เพิ่มงานวิจัย, ดูรายการงานวิจัยทั้งหมด, ลบงานวิจัย, แก้ไขข้อมูล
- นักวิจัย: ดูรายการงานวิจัยทั้งหมด

## Feature
1. หน้ารายการงานวิจัย
- ตารางแสดงเลขสัญญาทุน, ประเภทโครงการหลัก/ต่อเนื่อง, ชื่อ, สถานะ และกระบวนการ; ไม่แสดง ID ภายใน; ข้อมูลโครงการใหม่ใช้ฟิลด์ตาม AC-1 และ OpenAPI
- แสดงจำนวนรายการ และเน้นรายการที่เพิ่งเพิ่ม/แก้ไข

2. ค้นหาและกรองรายการ
- ค้นหาจากเลขสัญญาทุนแทน ID และค้นหาจากชื่อได้ตามเดิม กรองตามสถานะและกระบวนการบน frontend จากรายการที่โหลดมา
- กรองตามสถานะและกระบวนการ
- ปุ่มเปิด/ยุบแถบตัวกรอง และล้างตัวกรอง

3. เพิ่มงานวิจัย
- กรอกข้อมูลโครงการ บุคลากร แหล่งทุน ระยะเวลา งบประมาณ บทคัดย่อ วัตถุประสงค์ และคำสำคัญ พร้อมเลือก PDF ตาม AC-1
- หลังบันทึกสำเร็จกลับหน้ารายการและแสดงงานใหม่; มีปุ่มยกเลิกและย้อนกลับ
- เลือกเป็นโครงการตามงบประมาณ หรือโครงการต่อเนื่อง
- เมื่อเลือกงานต่อเนื่อง ให้ค้นหางานต้นทางด้วยเลขสัญญาทุนหรือชื่อและเลือกรายการ โดยระบบส่ง ID ของรายการที่เลือกภายใน ไม่ให้ผู้ใช้กรอก ID
- มี validation ฝั่งหน้าเว็บและข้อความแจ้งข้อผิดพลาด

4. แก้ไขงานวิจัย
- แก้ไขข้อมูลโครงการ บุคลากร แหล่งทุน และ PDF ตาม AC-6
- แสดงข้อมูลว่าเป็นงานต้นฉบับหรืองานต่อเนื่อง
- ไม่เปิดให้แก้รหัสหรือความสัมพันธ์ของงานต่อเนื่อง

5. ลบงานวิจัย
- มีหน้าต่างยืนยันก่อนลบ
- แจ้งเตือนว่าการลบย้อนกลับไม่ได้
- รองรับข้อผิดพลาด เช่น งานมีรายการต่อเนื่องอ้างอิงอยู่

6. สถานะการแสดงผลของรายการ
- Loading
- Error และปุ่มลองใหม่
- Empty state พร้อมปุ่มเพิ่มงานวิจัย
- Success/feedback หลังเพิ่ม แก้ไข หรือลบ

7. การนำทาง
- Sidebar แบบขยาย/ยุบ
- ปุ่มเข้ารายการงานวิจัยและปุ่มเพิ่มงานวิจัย

8. หน้าปรับสถานะงานวิจัย- หัวข้อ: “ปรับสถานะงานวิจัย”
- ช่องค้นหางานวิจัยจากเลขสัญญาทุนหรือชื่อ
- รายการผลลัพธ์: เลขสัญญาทุน, ชื่อ, สถานะปัจจุบัน, กระบวนการปัจจุบัน
- เมื่อเลือกงานวิจัย แสดงรายละเอียดสรุปและสถานะปัจจุบัน
- ส่วนเลือกสถานะใหม่ แสดงเฉพาะสถานะที่เปลี่ยนได้ตามลำดับ
- ปุ่ม “บันทึกสถานะ”
- กล่องยืนยันก่อนบันทึก
- ข้อความแจ้งผลสำเร็จ/ล้มเหลว เช่น
  - ไม่พบงานวิจัย
  - ไม่สามารถข้ามหรือย้อนสถานะ
  - โครงการเสร็จสิ้นหรือยุติแล้ว
- Loading, empty result, error และ success state

9. หน้าปรับกระบวนการงานวิจัย- หัวข้อ: “ปรับกระบวนการงานวิจัย”
- ช่องค้นหางานวิจัยจากเลขสัญญาทุนหรือชื่อ
- รายการผลลัพธ์: เลขสัญญาทุน, ชื่อ, สถานะ, กระบวนการปัจจุบัน
- เมื่อเลือกงานวิจัย แสดงรายละเอียดสรุปและลำดับกระบวนการ 8 ขั้น
- แสดงขั้นปัจจุบันและขั้นถัดไปอย่างชัดเจน
- เลือกกระบวนการใหม่ได้เฉพาะขั้นถัดไป หรือกด “ไปขั้นถัดไป”
- ปุ่ม “บันทึกกระบวนการ”
- กล่องยืนยันก่อนบันทึก
- แจ้งข้อผิดพลาด เช่น ข้ามขั้น, ย้อนขั้น, อยู่ขั้นสุดท้ายแล้ว หรือโครงการสิ้นสุดแล้ว
- Loading, empty result, error และ success state

## Out of scope (MVP v1)
- Authentication / user accounts
- Deployment
- Notificaton การแจ้งเตือนให้กับนักวิจัยเมื่องานวิจัยของตนถูกเปลี่ยนสถานะ
- การส่งออกข้อมูลในรูปแบบ Excel

## Acceptance Criteria

AC-01 — การเพิ่มงานวิจัย
- เมื่อกรอกข้อมูลจำเป็นครบและถูกต้อง กดบันทึกแล้วระบบสร้างงานวิจัยสำเร็จ
- ข้อมูลประกอบด้วย:
| กลุ่ม | ข้อมูล |
|---|---|
| โครงการ | ชื่อโครงการ, การเป็นทุนอุดหนุน, ประเภทโครงการ, โครงการในงบประมาณ/ต่อเนื่อง, งานต้นทางกรณีต่อเนื่อง |
| บุคลากร | หัวหน้าโครงการและผู้ร่วมโครงการ พร้อมชื่อ อีเมล หน่วยงาน และสัดส่วนการมีส่วนร่วม |
| แหล่งทุน | ประเภทภายใน/ภายนอก, ชื่อแหล่งทุน, เลขที่สัญญาทุน, ไฟล์สัญญา PDF |
| รายละเอียด | หน่วยงานรับผิดชอบโครงการและงบประมาณ, วันเริ่ม–สิ้นสุด, งบประมาณ, บทคัดย่อไทย/อังกฤษ, วัตถุประสงค์, คำสำคัญ |
    
- งานวิจัยหนึ่งรายการมีแหล่งทุนหนึ่งแหล่งและสัญญาหนึ่งฉบับ  
- สถานะเริ่มต้นเป็น “กำลังดำเนินการ” และกระบวนการเริ่มต้นเป็น “สัญญาโครงการ”
- หลังบันทึกสำเร็จ พากลับหน้ารายการ แสดงงานใหม่และข้อความยืนยัน
- ระหว่างบันทึก ป้องกันการกดส่งซ้ำ
- หากบันทึกล้มเหลว ไม่แสดงผลว่าสำเร็จ และเก็บข้อมูลที่กรอกไว้ให้แก้ไขหรือลองใหม่
AC-02 — รหัสงานวิจัย
- ระบบสร้าง ID เป็นจำนวนเต็มบวกที่ไม่ซ้ำ
- ID ใช้อ้างอิงภายในฐานข้อมูลและ API เท่านั้น ไม่แสดงหรือใช้เป็นช่องค้นหาใน UI; ใช้เลขสัญญาทุนสำหรับค้นหาแทน ID โดยยังค้นหาจากชื่อได้
- คง ID ใน response, path parameter และ continuationOfId เพื่อระบุรายการภายใน ไม่เปลี่ยน endpoint ให้ใช้เลขสัญญาทุน
- Client ไม่สามารถกำหนดหรือแก้ ID
- การแก้ข้อมูล สถานะ หรือกระบวนการไม่เปลี่ยน ID
- ไม่ใช้ ID ที่เคยลบแล้วซ้ำ และอนุญาตให้ลำดับ ID มีช่องว่าง
- การสร้างพร้อมกันต้องไม่ทำให้ ID ซ้ำ
AC-03 — งานต่อเนื่องและชื่อซ้ำ
- งานต้นฉบับไม่มีงานต้นทาง ส่วนงานต่อเนื่องต้องอ้างถึงงานที่มีอยู่
- หากไม่พบงานต้นทาง ปฏิเสธการบันทึกด้วย CONTINUATION_NOT_FOUND
- อ้างถึงงานที่เสร็จสิ้นหรือยุติแล้วได้
- หลังสร้าง ไม่สามารถเปลี่ยนความสัมพันธ์กับงานต้นทาง
- งานต้นฉบับห้ามใช้ชื่อซ้ำกับงานใดที่มีอยู่ หลังตัด Unicode whitespace หัวท้ายและเปรียบเทียบแบบ case-sensitive
- งานต่อเนื่องใช้ชื่อซ้ำได้ และไม่จำเป็นต้องชื่อเดียวกับงานต้นทาง
- หลายงานสามารถต่อยอดจากงานต้นทางเดียวกันได้
- กฎเหล่านี้ต้องถูกต้องแม้มีคำขอบันทึกพร้อมกัน
AC-04 — Validation ข้อมูลโครงการ
- ฟิลด์จำเป็นต้องมีค่าและมีชนิดข้อมูลถูกต้อง ยกเว้นข้อมูลที่ไม่เกี่ยวข้องตามเงื่อนไข เช่น งานต้นทางของงานต้นฉบับ
- ข้อความที่มีแต่ whitespace ถือว่าว่าง
- ฟิลด์ข้อความทั่วไปทั้งหมด ได้แก่ ชื่อโครงการ ชื่อบุคลากร หน่วยงาน ชื่อแหล่งทุน เลขที่สัญญาทุน หน่วยงานรับผิดชอบ บทคัดย่อไทย/อังกฤษ วัตถุประสงค์ และคำสำคัญ ต้องยาว 1–1,000 Unicode characters โดยนับ Unicode code points หลังตัด whitespace หัวท้าย
- อีเมลต้องยาว 1–254 Unicode characters หลังตัด whitespace หัวท้ายและผ่านรูปแบบอีเมลที่ API contract กำหนด
- ชื่อโครงการห้ามมี /, newline, tab และ control characters ตามกฎเดิม
- ค่าแบบตัวเลือกต้องเป็นหนึ่งในค่าที่ระบบรองรับ
- แสดงและรับวันที่เป็น DD/MM/YYYY ปี พ.ศ. และตรวจว่ามีวันดังกล่าวจริง
- วันสิ้นสุดห้ามว่างและต้องห่างจากวันเริ่มต้นอย่างน้อย 1 ปีปฏิทิน โดยเทียบวัน/เดือนเดียวกันในปี พ.ศ. ถัดไป
- หากวันครบรอบไม่มีอยู่จริงเพราะเริ่มวันที่ 29 กุมภาพันธ์และปีถัดไปไม่ใช่ปีอธิกสุรทิน ให้ใช้วันที่ 1 มีนาคมของปีถัดไปเป็นวันสิ้นสุดขั้นต่ำ เช่น เริ่ม `29/02/2567` สิ้นสุดขั้นต่ำ `01/03/2568`
- งบประมาณต้องมากกว่า 0 และมีทศนิยมไม่เกิน 2 ตำแหน่ง ไม่ปัดค่าที่ไม่ผ่านให้ผ่านโดยเงียบ ๆ
- ข้อมูลไม่ผ่านต้องแจ้งฟิลด์ที่ผิด และไม่บันทึกบางส่วน
AC-05 — บุคลากรในโครงการ
- รองรับบุคลากรหลายคน และเก็บแยกจากตารางงานวิจัยโดยเชื่อมด้วย ID งานวิจัย
- แต่ละคนต้องมีชื่อ อีเมล หน่วยงาน สัดส่วนการมีส่วนร่วม และบทบาท
- อีเมลต้องผ่านรูปแบบที่กำหนด
- แยกบทบาทหัวหน้าโครงการและผู้ร่วมโครงการได้
- หากบุคลากรรายใดไม่ผ่าน validation ต้องปฏิเสธการบันทึกทั้งโครงการ
- ต้องมีหัวหน้าโครงการ 1 คนและผู้ร่วมโครงการ 1 คนเท่านั้น รวม 2 คน ทั้งตอนสร้างและแก้ไข
- คนเดียวเป็นทั้งสองบทบาทในโครงการเดียวกันไม่ได้ ใช้อีเมลตรวจบุคคลซ้ำภายในโครงการ
- สัดส่วนการมีส่วนร่วมของทั้งสองคนต้องรวมเท่ากับ 100% หากไม่ครบหรือเกินให้ปฏิเสธทั้งโครงการ
- ตรวจอีเมลซ้ำภายในโครงการโดยตัด whitespace หัวท้ายและเปรียบเทียบแบบไม่แยกตัวพิมพ์ใหญ่–เล็ก เช่น ` User@example.com ` กับ `user@example.com` ถือว่าซ้ำกัน ทั้งตอนสร้างและแก้ไข
AC-06 — ไฟล์สัญญา
- รับเฉพาะ PDF ขนาดไม่เกิน 20 MiB (20,971,520 bytes)
- ตรวจชนิดไฟล์จากเนื้อหา ไม่เชื่อเฉพาะนามสกุลหรือ Content-Type
- การเลือกไฟล์ก่อนกดบันทึกยังไม่สร้างไฟล์ถาวรในระบบ
- เมื่อกดยกเลิกก่อนบันทึก ต้องไม่มีข้อมูลหรือไฟล์ถาวรถูกสร้าง
- ระบบรายงานสำเร็จเมื่อข้อมูลและไฟล์พร้อมใช้งานครบแล้ว
- หากขั้นตอนใดล้มเหลว ต้องไม่เหลืองานวิจัยที่อ้างถึงไฟล์ซึ่งไม่มีอยู่ และต้องจัดการไฟล์ชั่วคราวที่เกิดขึ้น
- ไม่ส่งตำแหน่งไฟล์ภายในเซิร์ฟเวอร์ให้ client
- คำขอ `multipart/form-data` ทั้งก้อนจำกัด 21 MiB (22,020,096 bytes) แยกจากเพดานเนื้อหา PDF 20 MiB; หากเกินเพดานใดเพดานหนึ่งให้ตอบ 413 PAYLOAD_TOO_LARGE และไม่บันทึกข้อมูลหรือไฟล์ถาวร
AC-07 — แสดงรายการงานวิจัย
- โหลดรายการผ่าน API และใช้ ID ระบุรายการ แม้ชื่อซ้ำ
- แสดงข้อมูลตามคอลัมน์ที่กำหนดสำหรับรูปแบบโครงการใหม่ พร้อมจำนวนรายการ
- เรียงตามชื่อและใช้ ID เป็นลำดับรองเมื่อชื่อซ้ำ ตามกฎเดิม
- ไม่มีข้อมูลให้แสดง empty state
- โหลดไม่สำเร็จให้แสดง error และปุ่มลองใหม่
- หลังเพิ่มหรือแก้ไข แสดงข้อมูลล่าสุดและระบุรายการที่เพิ่งเปลี่ยน
- ไม่แสดงคอลัมน์ description เดิม
AC-08 — ค้นหาและกรอง
- ค้นหาและกรองบน frontend จากรายการที่ API โหลดมา ตามแนวทางที่เลือกไว้ก่อนหน้า
- ค้นหาจากเลขสัญญาทุนหรือชื่อ ไม่ค้นหาจาก ID และกรองด้วยสถานะกับกระบวนการ
- ก่อนค้นหาให้ตัด Unicode whitespace หัวท้ายและเปรียบเทียบแบบไม่แยกตัวพิมพ์ใหญ่–เล็กด้วย Unicode case folding; คำค้นต้องตรงกับบางส่วนของชื่อหรือเลขสัญญาทุน และคำค้นว่างไม่จำกัดผลลัพธ์
- เลขสัญญาทุนต้องไม่ซ้ำกันทั้งระบบหลัง normalize ด้วยกฎเดียวกัน; การสร้างพร้อมกันด้วยเลขสัญญาทุนเดียวกันต้องสำเร็จเพียงรายการเดียว อีกคำขอตอบ CONTRACT_NUMBER_ALREADY_EXISTS
- เมื่อใช้หลายตัวกรอง ผลลัพธ์ต้องผ่านทุกเงื่อนไขที่เลือก
- ปุ่มกรองเปิด/ยุบส่วนกรอกเงื่อนไขได้ โดยการยุบไม่ล้างเงื่อนไข
- ปุ่มล้างตัวกรองคืนค่าทั้งหมดและแสดงรายการที่โหลดมา
- แสดงจำนวนที่พบเทียบกับทั้งหมด
- แยกข้อความ “ไม่มีงานวิจัย” กับ “ไม่พบรายการตามเงื่อนไข”
- ไม่ค้นหาฟิลด์อื่นนอกเหนือจากชื่อและเลขสัญญาทุน และไม่มีฟิลด์ description
AC-09 — แก้ไขงานวิจัย
- เปิดฟอร์มด้วยข้อมูลปัจจุบันของงานที่เลือกตาม ID
- แก้ไขเฉพาะฟิลด์ที่กำหนดให้แก้ได้ และใช้ validation เดียวกับการสร้าง
- ห้ามเปลี่ยน ID งานต้นทาง สถานะ หรือกระบวนการผ่านการแก้ข้อมูลทั่วไป
- การเปลี่ยนชื่อยังต้องผ่านกฎชื่อซ้ำ
- บันทึกสำเร็จแล้วแสดงข้อมูลล่าสุด
- หากบันทึกล้มเหลว ข้อมูลเดิมต้องคงอยู่ครบ
- หากงานถูกลบไปแล้ว แจ้ง RESEARCH_NOT_FOUND
- การแก้ไขไม่บังคับเลือก PDF ใหม่ หากไม่ส่ง `contractFile` ต้องเก็บไฟล์และ metadata เดิมไว้
- หากส่ง PDF ใหม่ ต้องตรวจด้วยกฎเดียวกับการสร้างและแทนที่ไฟล์เดิมเมื่อการแก้ไขสำเร็จเท่านั้น; หากล้มเหลวต้องเก็บข้อมูลและไฟล์เดิมครบและกำจัดไฟล์ชั่วคราว
AC-10 — ลบงานวิจัย
- แสดงชื่อและเลขสัญญาทุนในหน้าต่างยืนยันก่อนลบ ไม่แสดง ID ภายใน
- ยกเลิกแล้วข้อมูลไม่เปลี่ยน
- ห้ามลบงานที่มีงานต่อเนื่องอ้างถึง พร้อมแจ้ง RESEARCH_HAS_CONTINUATIONS
- ลบสำเร็จแล้วงาน ข้อมูลบุคลากร metadata สัญญา และไฟล์ PDF ที่เกี่ยวข้องต้องถูกลบทั้งหมด
- ลบซ้ำหรือไม่พบงาน ให้แจ้ง RESEARCH_NOT_FOUND
- เมื่อเกิดข้อผิดพลาด ต้องไม่ลบข้อมูลเพียงบางส่วน
- หากลบข้อมูลหรือไฟล์ PDF ไม่สำเร็จ ต้องถือว่าการลบล้มเหลวและคงข้อมูลกับไฟล์เดิมให้ใช้งานได้ ห้ามรายงาน 204 ขณะที่ยังมีข้อมูลหรือไฟล์ค้างจากรายการนั้น
AC-11 — ปรับสถานะ
- เลือกงานจากเลขสัญญาทุนหรือชื่อ และแสดงสถานะปัจจุบันก่อนปรับ
- ค่าสถานะใช้ข้อความตรงตัว: `กำลังดำเนินการ` → `กำลังดำเนินการ(ขยายเวลาครั้งที่ 1)` → `กำลังดำเนินการ(ขยายเวลาครั้งที่ 2)` → `กำลังดำเนินการ(ขยายเวลามากกว่า 2 ครั้ง)` และสถานะสิ้นสุดคือ `โครงการเสร็จสิ้น`, `ยุติโครงการ`
- ห้ามข้ามหรือย้อนขั้นปกติ
- จากสถานะปกติใดก็ได้ เปลี่ยนเป็น “โครงการเสร็จสิ้น” หรือ “ยุติโครงการ” ได้
- เมื่อจบโครงการแล้ว ห้ามเปลี่ยนสถานะเป็นค่าอื่น
- ส่งสถานะเดิมซ้ำให้สำเร็จโดยไม่เปลี่ยนข้อมูล รวมสถานะสิ้นสุดเดิม
- การปรับสถานะไม่เปลี่ยนกระบวนการหรือข้อมูลอื่น
- UI แสดงเฉพาะตัวเลือกที่อนุญาต ยืนยันก่อนบันทึก และแจ้งผลลัพธ์
- Backend ต้องตรวจสิทธิ์การเปลี่ยนตามกฎสถานะอีกครั้ง แม้เรียก API โดยตรง
AC-12 — ปรับกระบวนการ
- รองรับข้อความตรงตัว 8 ขั้นตาม AGENTS: `สัญญาโครงการ` → `บันทึกข้อตกลง` → `เปิดบัญชีธนาคาร` → `การเบิกจ่ายเงิน` → `การจัดสรรค่าธรรมเนียม` → `การติดตามส่งรายงาน` → `รายงานสรุปการใช้เงิน` → `การปิดบัญชีธนาคาร`
- มีขั้นปัจจุบันเพียงหนึ่งขั้น และเปลี่ยนไปได้เฉพาะขั้นถัดไป
- ห้ามข้าม ย้อน หรือเปลี่ยนต่อจากขั้นสุดท้าย
- ส่งขั้นเดิมซ้ำให้สำเร็จโดยไม่เปลี่ยนข้อมูล หากโครงการยังไม่สิ้นสุด
- หากโครงการเสร็จสิ้นหรือยุติแล้ว ปฏิเสธการปรับกระบวนการ รวมคำขอส่งขั้นเดิม
- กระบวนการไม่เปลี่ยนสถานะ และไม่ทำให้โครงการเสร็จสิ้นอัตโนมัติ
- UI แสดงขั้นปัจจุบัน ขั้นถัดไป และยืนยันก่อนบันทึก
AC-13 — ความถูกต้องและข้อผิดพลาดร่วม
- ข้อมูลโครงการ บุคลากร และความสัมพันธ์ต้องบันทึกแบบสำเร็จครบหรือย้อนกลับทั้งหมด
- การปรับสถานะ/กระบวนการพร้อมกันต้องตรวจค่าล่าสุดและบันทึกอย่าง atomic
- งานต้นฉบับชื่อเดียวกันที่สร้างพร้อมกัน ต้องสำเร็จเพียงรายการเดียว
- UI ต้องปิดปุ่มส่งระหว่างคำขอกำลังทำงานและไม่ retry mutation อัตโนมัติ; การเรียก POST ซ้ำถือเป็นคำขอสร้างใหม่และยังต้องผ่านกฎชื่อกับเลขสัญญาทุนซ้ำ
- การแก้ไขข้อมูลทั่วไปพร้อมกันใช้ last-successful-write-wins โดยไม่มี version หรือ If-Match; response ของแต่ละคำขอเป็นข้อมูลที่คำขอนั้นบันทึกสำเร็จ ส่วนการโหลดครั้งถัดไปต้องได้ค่าจากการเขียนที่สำเร็จล่าสุด
- Error ใช้รูปแบบ {"error":{"code":"...","message":"..."}}
- VALIDATION_ERROR ต้องเพิ่ม `fieldErrors` เป็น array ที่ไม่ว่าง แต่ละรายการมี `field` เป็น path ของฟิลด์ เช่น `projectMembers[0].email` และ `message` ที่อ่านได้; error code อื่นไม่มี `fieldErrors`
- ไม่เปิดเผย SQL, stack trace หรือข้อมูลภายในระบบ
- ตรวจชนิดข้อมูล ฟิลด์เกิน ฟิลด์ซ้ำ เนื้อหาผิดรูปแบบ และขนาด request ตาม contract ของแต่ละ operation
- Health check แยกกรณีปกติ ฐานข้อมูลไม่พร้อม และข้อผิดพลาดภายใน
- เส้นทางที่ไม่มีตอบ 404 และ method ที่ไม่รองรับตอบ 405 ตาม contract เดิม
AC-14 — การนำทางและการใช้งาน UI
- Sidebar ขยาย/ยุบได้ และเข้าถึงหน้าที่อยู่ในขอบเขตได้
- หน้าเพิ่มงานวิจัยมีปุ่มย้อนกลับและยกเลิกกลับหน้ารายการ
- หากมีข้อมูลที่ยังไม่บันทึก ให้ยืนยันก่อนทิ้งข้อมูล
- ทุกหน้าที่โหลดข้อมูลมี loading, error, empty และ success ตามบริบท
- ฟอร์มและปุ่มใช้งานด้วย keyboard ได้ มี label และ focus ที่มองเห็น
- ตรวจ responsive อย่างน้อยที่ viewport 375×667 และ 1280×720 โดยเนื้อหา/ปุ่มไม่ถูกตัดและไม่เกิด horizontal scroll ทั้งหน้า (ตารางเลื่อนใน container ของตนได้)
- สีข้อความและส่วนควบคุมต้องผ่าน WCAG 2.2 AA: contrast อย่างน้อย 4.5:1 สำหรับข้อความปกติและ 3:1 สำหรับข้อความขนาดใหญ่/องค์ประกอบ UI
- ทุก action ใช้ keyboard ได้ตามลำดับที่มองเห็น มี focus indicator ชัดเจน และเมื่อเปิด dialog/dropdown ให้จัดการ focus และ Escape ตามชนิดองค์ประกอบ
- เมื่อ `prefers-reduced-motion: reduce` ให้ปิด animation ที่ไม่จำเป็นและทำให้ transition ที่จำเป็นเกิดทันที

{"error": {"code": "MACHINE_READABLE_CODE", "message": "human readable"}}

## SQL
- หัวข้อนี้เป็นข้อกำหนด schema เป้าหมาย ไม่ใช่คำสั่งให้ล้างฐานข้อมูลหรือไฟล์ทุกครั้งที่เริ่ม server; migration และข้อมูลสำรองต้องจัดการแยกจาก runtime
- ตาราง `researches` ต้องมี `id`, `title`, `is_subsidized`, `project_type`, `research_kind`, `continuation_of_id`, `responsible_project_unit`, `responsible_budget_unit`, `start_date`, `end_date`, `budget_amount`, `thai_abstract`, `english_abstract`, `objectives`, `keywords`, `status` และ `process`
- `id` เป็น integer บวกที่ SQLite สร้าง เป็น primary key แบบไม่ใช้ค่าซ้ำหลังลบ และห้ามแก้ไข
- `continuation_of_id` เป็น nullable self-reference foreign key; ห้ามแก้ไข และใช้ `ON UPDATE RESTRICT` กับ `ON DELETE RESTRICT`
- ตาราง `research_members` เป็นความสัมพันธ์หนึ่งต่อหลายกับ `researches`; เก็บ `full_name`, `email`, `affiliation`, `contribution_percent` และ `role` แบบ `NOT NULL` โดย role อยู่ใน `LEAD`,`CO_RESEARCHER` และ percentage อยู่ใน `(0,100]` มีทศนิยมไม่เกิน 2 ตำแหน่ง
- ตาราง `research_contracts` เป็นหนึ่งต่อหนึ่งกับ `researches`; เก็บ `funding_type`, `funding_source_name`, `contract_number`, `storage_path`, `original_filename`, `content_type`, `size_bytes` และบังคับ `content_type='application/pdf'`, `size_bytes <= 20971520`
- เก็บ `contract_number_key` ที่ service สร้างด้วย Unicode trim และ case folding เป็น `NOT NULL UNIQUE` เพื่อบังคับเลขสัญญาทุนไม่ซ้ำภายใต้ concurrent writes; client ไม่รับหรือส่ง key นี้
- ข้อมูลข้อความใหม่เป็น `NOT NULL` และบังคับความยาว/อักขระตาม AC-04; `budget_amount > 0` และมี precision 2 ตำแหน่ง; วันจัดเก็บแบบ canonical ที่ตรวจสอบได้ แต่ API รับ/ตอบ `DD/MM/YYYY` ปี พ.ศ. และบังคับวันสิ้นสุดขั้นต่ำตาม AC-04
- `status` เป็น `NOT NULL` ค่าเริ่มต้น "กำลังดำเนินการ" และรับเฉพาะหกค่าที่ระบุใน AC-11
- `process` เป็น `NOT NULL` ค่าเริ่มต้น "สัญญาโครงการ" และรับเฉพาะแปดค่าที่ระบุใน AC-12
- constraint/index/trigger ต้องบังคับกฎ title ของงานต้นฉบับและงานต่อเนื่องให้ถูกต้องภายใต้ concurrent writes
- trigger ต้องห้ามแก้ `id` และ `continuation_of_id` หลังสร้าง
- trigger ต้องบังคับ status transition, process transition, terminal lock และการคง process เดิมเมื่อเข้าสู่ terminal status ตาม AC-11 และ AC-12
- ทุก connection ต้องเปิด foreign keys และทุก mutation ต้องทำใน transaction แบบ atomic; การเขียนไฟล์ใช้ staging และชื่อไฟล์ถาวรที่ระบบสร้าง ไม่ใช้ชื่อจาก client เป็น path
- PDF ต้อง parse ได้จนจบ มีอย่างน้อย 1 หน้า ไม่เสียหายและไม่เข้ารหัส/ป้องกันด้วยรหัสผ่าน; ไฟล์ที่ไม่ผ่านตอบ VALIDATION_ERROR ที่ `contractFile`
- วางไฟล์ใหม่ในตำแหน่งถาวรก่อน commit metadata; หาก transaction ล้มเหลวให้ลบไฟล์ใหม่ เมื่อ update สำเร็จจึงลบไฟล์เก่า และลบไฟล์ถาวรที่ไม่มี metadata อ้างอิงเมื่อเริ่ม server
- การลบใช้ staging เพื่อย้อนคืนไฟล์ได้ก่อน transaction commit; เมื่อเริ่ม server หาก staged deletion ยังมี metadata อ้างอิงให้คืนไฟล์ มิฉะนั้นให้ลบทิ้ง รวมทั้งล้าง upload staging ที่ค้าง เพื่อไม่ให้ crash ทิ้งข้อมูลอ้างไฟล์ที่หายหรือไฟล์กำพร้า
