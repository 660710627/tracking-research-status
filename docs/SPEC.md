# SPEC Tracking-Research-Status MVP
## การปรับกฎสถานะและกระบวนการที่อนุมัติ (25 กันยายน 2026)
- ผู้ประสานงานและผู้ดูแลระบบเปลี่ยนสถานะไปยังสถานะอื่นใดได้ทั้งย้อนกลับและเดินหน้า รวมถึงออกจากสถานะโครงการเสร็จสิ้นและยุติโครงการ
- เปลี่ยนกระบวนการไปยังขั้นใดก็ได้จาก 8 ขั้นในทุกสถานะ โดยการเปลี่ยนกระบวนการไม่เปลี่ยนสถานะและการเปลี่ยนสถานะไม่เปลี่ยนกระบวนการ
- ยังคงแสดงการยืนยันก่อนเปลี่ยนแปลง และนักวิจัยไม่มีสิทธิ์ปรับสถานะหรือกระบวนการ
- ข้อกำหนดนี้แทนที่ข้อจำกัด forward-only และ terminal lock สำหรับสถานะ/กระบวนการในเอกสารฉบับนี้ การแก้ไข SDGs ขณะยุติโครงการยังคงถูกล็อกตามข้อกำหนดเฉพาะ SDGs
- ดำเนินการแล้วใน frontend demo; การเชื่อม API และฐานข้อมูลจริงต้องใช้กฎใหม่นี้ในรอบพัฒนา backend

## ขอบเขต demo SDGs ที่อนุมัติ
- หน้าเพิ่มงานวิจัยต้องเลือก SDGs อย่างน้อย 1 เป้าหมายจาก 17 เป้าหมาย เลือกได้หลายรายการและไม่ซ้ำกัน
- หน้ารายละเอียดแสดงหมายเลขและชื่อ SDGs พร้อมส่วนแก้ไขแยกจากข้อมูลทั่วไป มีบันทึกและยกเลิก
- ทุกบทบาทแก้ไข SDGs ของงานวิจัยที่แสดงได้ เป็นข้อยกเว้นเฉพาะ demo จากสิทธิ์อ่านอย่างเดียวของนักวิจัย นักวิจัยยังแก้ไขข้อมูลทั่วไป สถานะ และกระบวนการไม่ได้
- สถานะยุติโครงการล็อกการแก้ไข SDGs สำหรับทุกบทบาท ส่วนโครงการเสร็จสิ้นยังแก้ไข SDGs ได้
- เก็บข้อมูลในหน่วยความจำและรีเซ็ตเมื่อโหลดหน้าใหม่ รอบนี้ไม่เปลี่ยน production API หรือฐานข้อมูล; ต้องออกแบบ contract และ constraints ก่อนเชื่อมระบบจริง

## Users
- ผู้ดูแลระบบ: เพิ่มงานวิจัย, ดูรายการงานวิจัยทั้งหมด, ลบงานวิจัย, แก้ไขข้อมูล, มองเห็นโมดูลระบบจัดการข้อมูลพื้นฐานและโมดุลย่อยภายในผ่านแทบทางด้านซ้าย
- ผู้ประสานงาน: เพิ่มงานวิจัย, ดูรายการงานวิจัยทั้งหมด, ลบงานวิจัย, แก้ไขข้อมูล
- นักวิจัย: ดูรายการงานวิจัยทั้งหมด

# Acceptance Criteria ระบบบริหารจัดการและติดตามสถานะงานวิจัย

## ผู้ใช้และสิทธิ์

**AC-01 การเข้าสู่ระบบและสถานะบัญชี**  
เมื่อผู้ใช้เข้าสู่ระบบ ระบบต้องระบุตัวตน บทบาท และสถานะบัญชีของผู้ใช้นั้นได้ ผู้ใช้ที่ยังไม่ได้รับอนุมัติหรือถูกระงับต้องไม่สามารถใช้งานส่วนที่ต้องมีสิทธิ์ได้ และต้องได้รับข้อความแจ้งสถานะบัญชีที่เข้าใจได้

**AC-02 การอนุมัติบัญชี**  
เมื่อผู้ใช้เข้าสู่ระบบครั้งแรกและบัญชีรออนุมัติ ผู้ดูแลระบบต้องเห็นบัญชีดังกล่าวในรายการอนุมัติและดำเนินการอนุมัติได้ หลังอนุมัติ สิทธิ์ที่ใช้งานได้ต้องตรงกับบทบาทที่กำหนด

**AC-03 สิทธิ์ของนักวิจัย**  
นักวิจัยต้องดูรายการ รายละเอียด สถานะ และกระบวนการของงานวิจัยที่ตนมีสิทธิ์เข้าถึงได้ แต่ต้องไม่สามารถเพิ่ม แก้ไข ลบ หรือปรับสถานะและกระบวนการ ไม่ว่าจะดำเนินการผ่านหน้าจอหรือเรียก API โดยตรง

**AC-04 สิทธิ์ของผู้ประสานงานและผู้ดูแลระบบ**  
ผู้ประสานงานและผู้ดูแลระบบต้องสามารถเพิ่ม ดู แก้ไข ลบ และปรับสถานะหรือกระบวนการของงานวิจัยได้ ผู้ดูแลระบบต้องเข้าถึงโมดูลจัดการข้อมูลพื้นฐานและรายงาน Log ได้ ส่วนผู้ประสานงานและนักวิจัยต้องไม่สามารถดำเนินการในโมดูลที่สงวนไว้สำหรับผู้ดูแลระบบ

**AC-05 การจัดการบัญชีผู้ใช้งาน**  
ผู้ดูแลระบบต้องดูบัญชีทั้งหมดและแก้ไขชื่อ ตำแหน่ง อีเมล และสิทธิ์การใช้งานได้ เมื่อระงับบัญชี ระบบต้องปฏิเสธการใช้งานที่ต้องมีสิทธิ์ของบัญชีนั้น การเปลี่ยนสิทธิ์ต้องมีผลต่อการตรวจสิทธิ์ครั้งถัดไป

## ข้อมูลงานวิจัย

**AC-06 การเพิ่มงานวิจัย**
- เมื่อกรอกข้อมูลจำเป็นครบและถูกต้อง กดบันทึกแล้วระบบสร้างงานวิจัยสำเร็จ
- ข้อมูลประกอบด้วย:
| กลุ่ม | ข้อมูล |
|---|---|
| โครงการ | ชื่อโครงการ, การเป็นทุนอุดหนุน, ประเภทโครงการ, โครงการในงบประมาณ/ต่อเนื่อง, งานต้นทางกรณีต่อเนื่อง |
| บุคลากร | หัวหน้าโครงการและผู้ร่วมโครงการ พร้อมชื่อ อีเมล หน่วยงาน และสัดส่วนการมีส่วนร่วม |
| แหล่งทุน | ประเภทภายใน/ภายนอก, ชื่อแหล่งทุน, เลขที่สัญญาทุน, ไฟล์สัญญา PDF |
| รายละเอียด | หน่วยงานรับผิดชอบโครงการและงบประมาณ, วันเริ่ม–สิ้นสุด, งบประมาณ, บทคัดย่อไทย/อังกฤษ, วัตถุประสงค์, คำสำคัญ |
    
- งานวิจัยหนึ่งรายการมีแหล่งทุนหนึ่งแหล่งและสัญญาหนึ่งฉบับ  
- สถานะเริ่มต้นเป็น “กำลังดำเนินการ” และกระบวนการเริ่มต้นเป็น “สัญญาโครงการ”
- หลังบันทึกสำเร็จ พากลับหน้ารายการ แสดงงานใหม่และข้อความยืนยัน
- ระหว่างบันทึก ป้องกันการกดส่งซ้ำ
- หากบันทึกล้มเหลว ไม่แสดงผลว่าสำเร็จ และเก็บข้อมูลที่กรอกไว้ให้แก้ไขหรือลองใหม่

**AC-07 ความครบถ้วนของข้อมูลโครงการ**  
ระบบต้องรับและแสดงชื่อโครงการ การเป็นทุนอุดหนุนหรือประเภทที่เกี่ยวข้อง ประเภทโครงการว่าเป็นงานวิจัยหรือบริการวิชาการ และลักษณะการดำเนินงานว่าเป็นโครงการในงบประมาณหรือโครงการต่อเนื่อง ข้อมูลที่บันทึกต้องตรงกับข้อมูลที่แสดงเมื่อเปิดรายละเอียดอีกครั้ง

**AC-08 บุคลากรของโครงการ**  
ระบบต้องแยกหัวหน้าโครงการกับผู้ร่วมโครงการ และเก็บความสัมพันธ์ของบุคลากรกับงานวิจัยที่ถูกต้อง เมื่อแก้ไขข้อมูลบุคลากรของโครงการหนึ่ง ต้องไม่ทำให้ข้อมูลบุคลากรของโครงการอื่นเปลี่ยนโดยไม่ตั้งใจ

**AC-09 แหล่งทุนและสัญญารับทุน**  
ระบบต้องเก็บประเภทแหล่งทุนว่าเป็นภายในหรือภายนอก ชื่อแหล่งทุน เลขที่สัญญาทุน และไฟล์สัญญารับทุน เมื่อเปิดรายละเอียดงานวิจัย ผู้มีสิทธิ์ต้องเห็นข้อมูลสัญญาที่ตรงกับรายการนั้น และไฟล์ที่บันทึกต้องเปิดใช้งานได้

**AC-10 รายละเอียดและระยะเวลาโครงการ**  
ระบบต้องเก็บหน่วยงานรับผิดชอบโครงการ หน่วยงานรับผิดชอบงบประมาณ วันเริ่มและสิ้นสุด งบประมาณ บทคัดย่อภาษาไทยและภาษาอังกฤษ วัตถุประสงค์ และคำสำคัญ วันที่ต้องเป็นวันที่มีอยู่จริง วันสิ้นสุดต้องไม่ก่อนวันเริ่ม และงบประมาณต้องเป็นค่าที่ใช้คำนวณได้

**AC-11 ID งานวิจัย**  
เมื่อสร้างงานวิจัย ระบบต้องกำหนด ID เป็นจำนวนเต็มบวกที่ไม่ซ้ำกัน ผู้ใช้ต้องกำหนดหรือแก้ไข ID ไม่ได้ ID ต้องคงเดิมหลังแก้ไขข้อมูลหรือปรับสถานะ และ ID ที่เคยใช้กับงานที่ลบแล้วต้องไม่ถูกนำกลับมาใช้ใหม่ แม้มีการสร้างงานวิจัยพร้อมกัน

**AC-12 งานวิจัยต่อเนื่องและชื่อซ้ำ**  
ระบบต้องระบุได้ว่างานวิจัยใดเป็นงานต่อเนื่องจากงานก่อนหน้า งานต่อเนื่องสามารถมีชื่อซ้ำได้ หากระบุงานต้นทาง ระบบต้องตรวจว่างานต้นทางมีอยู่จริงและแสดงความเชื่อมโยงให้ผู้ใช้เข้าใจได้ ระบบต้องไม่อนุญาตให้ใช้ชื่อซ้ำโดยอาศัยการระบุเป็นงานต่อเนื่องที่ไม่ถูกต้อง

**AC-13 การดูรายการและรายละเอียด**  
ผู้ใช้ต้องเปิดรายการงานวิจัยและดูรายละเอียดของแต่ละงานได้ แม้หลายงานมีชื่อเหมือนกัน ระบบต้องเปิดรายการที่ผู้ใช้เลือกได้ถูกต้อง และแสดงสถานะกับกระบวนการปัจจุบันของแต่ละงานอย่างชัดเจน

**AC-14 การค้นหาและกรอง**  
ผู้ใช้ต้องค้นหางานวิจัยจากข้อมูลที่แสดงและเลือกเงื่อนไขกรองเพื่อหางานที่ต้องการติดตามได้ เมื่อไม่มีงานในระบบหรือไม่พบงานตามเงื่อนไข ระบบต้องแสดงข้อความแยกสองกรณีนี้อย่างชัดเจน การล้างเงื่อนไขต้องกลับไปแสดงรายการตามสิทธิ์ของผู้ใช้

**AC-15 การแก้ไขงานวิจัย**  
เมื่อผู้มีสิทธิ์เปิดแก้ไข ระบบต้องแสดงข้อมูลปัจจุบัน เมื่อบันทึกข้อมูลที่ถูกต้อง ระบบต้องแสดงข้อมูลใหม่หลังโหลดอีกครั้ง การแก้ไขข้อมูลทั่วไปต้องไม่เปลี่ยน ID สถานะ หรือกระบวนการ หากบันทึกล้มเหลว ข้อมูลเดิมต้องยังอยู่ครบ

**AC-16 การลบงานวิจัย**  
ระบบต้องให้ผู้มีสิทธิ์ยืนยันงานที่ต้องการลบก่อนดำเนินการ หากยกเลิก ต้องไม่มีข้อมูลเปลี่ยน เมื่อการลบสำเร็จ งานวิจัยและข้อมูลประกอบที่เกี่ยวข้องต้องไม่ปรากฏเป็นรายการที่ใช้งานได้อีก หากลบไม่สำเร็จ ระบบต้องไม่รายงานว่าสำเร็จหรือปล่อยให้ข้อมูลถูกลบเพียงบางส่วน

## การติดตามความคืบหน้า

**AC-17 การแสดงสถานะงานวิจัย**  
ระบบต้องแสดงสถานะปัจจุบันเป็นหนึ่งในหกค่า ได้แก่ กำลังดำเนินการ, ขยายเวลาครั้งที่ 1, ขยายเวลาครั้งที่ 2, ขยายเวลามากกว่า 2 ครั้ง, โครงการเสร็จสิ้น หรือยุติโครงการ ผู้ใช้ต้องดูสถานะดังกล่าวได้จากหน้าติดตามงานวิจัย

**AC-18 การปรับสถานะงานวิจัย**  
เฉพาะผู้ประสานงานและผู้ดูแลระบบเท่านั้นที่ปรับสถานะได้ ก่อนบันทึก ระบบต้องแสดงสถานะเดิมและสถานะที่จะเปลี่ยน เมื่อเปลี่ยนสถานะไปข้างหน้าแล้ว ระบบต้องปฏิเสธการเปลี่ยนย้อนกลับ ทั้งหน้าจอและฐานข้อมูลต้องบังคับกฎเดียวกัน

**AC-19 การแสดงกระบวนการงานวิจัย**  
ระบบต้องแสดงกระบวนการปัจจุบันจากแปดกระบวนการหลัก ได้แก่ สัญญาโครงการ, บันทึกข้อตกลง, เปิดบัญชีธนาคาร, การเบิกจ่ายเงิน, การจัดสรรค่าธรรมเนียม, การติดตามส่งรายงาน, รายงานสรุปการใช้เงิน และการปิดบัญชีธนาคาร โดยผู้ใช้ต้องมองเห็นได้ว่าขณะนี้งานอยู่ในกระบวนการใด

**AC-20 การปรับกระบวนการงานวิจัย**  
เฉพาะผู้ประสานงานและผู้ดูแลระบบเท่านั้นที่ปรับกระบวนการได้ หน้าจอต้องทำให้การเลือกงาน ตรวจขั้นปัจจุบัน และบันทึกขั้นใหม่ทำได้สะดวก เมื่อบันทึกสำเร็จ กระบวนการใหม่ต้องปรากฏในรายการและหน้ารายละเอียดโดยไม่เปลี่ยนสถานะหรือข้อมูลอื่นโดยไม่ตั้งใจ

## ข้อมูลพื้นฐานและการตรวจสอบย้อนหลัง

**AC-21 ตำแหน่งทางวิชาการ**  
ผู้ดูแลระบบต้องเพิ่ม แก้ไข และลบตำแหน่งทางวิชาการได้ ตำแหน่งที่ใช้งานได้ต้องปรากฏเป็นตัวเลือกในจุดที่ระบบให้เลือกตำแหน่ง และการเปลี่ยนข้อมูลตำแหน่งต้องไม่ทำให้ข้อมูลผู้ใช้เดิมเสียหาย

**AC-22 ข้อมูลเกี่ยวกับเราและหน่วยงาน**  
ระบบต้องมีหน้าข้อมูลเกี่ยวกับสำนักงาน สวนส. และข้อมูลพื้นฐาน ได้แก่ ชื่อมหาวิทยาลัย ชื่อสำนักงาน ชื่อระบบ และที่อยู่ ผู้ดูแลระบบต้องจัดการข้อมูลที่กำหนดให้แก้ไขได้ และข้อมูลที่เผยแพร่บนหน้าเว็บต้องตรงกับค่าล่าสุดที่บันทึกสำเร็จ

**AC-23 รายงาน Log**  
ระบบต้องบันทึกเหตุการณ์การเปลี่ยนแปลงข้อมูลที่กำหนดให้ตรวจสอบย้อนหลัง เมื่อผู้ดูแลระบบเปิดรายงาน ต้องระบุได้ว่าเกิดการกระทำใด กับข้อมูลใด เมื่อใด และโดยบัญชีใด ผู้ใช้บทบาทอื่นต้องไม่เข้าถึงรายงานนี้

## คุณภาพและความถูกต้องของระบบ

**AC-24 ข้อผิดพลาดและความถูกต้องของข้อมูล**  
เมื่อคำขอไม่สำเร็จ API ต้องส่งข้อผิดพลาดในรูปแบบ `{"error":{"code":"...","message":"..."}}` อย่างสม่ำเสมอ ระบบต้องไม่เปิดเผยข้อมูลภายในที่ไม่เกี่ยวกับการแก้ปัญหาของผู้ใช้ กฎสำคัญเรื่องสิทธิ์ ID ชื่อซ้ำ และการเปลี่ยนสถานะต้องถูกตรวจที่ฝั่งระบบและบังคับในฐานข้อมูลตามความเหมาะสม

**AC-25 สถานะหน้าจอและการเข้าถึง**  
ทุกหน้าที่เรียกข้อมูลต้องรองรับการกำลังโหลด การแสดงผลสำเร็จ การไม่มีข้อมูล และข้อผิดพลาด ฟอร์มต้องแจ้งผลบันทึกที่ชัดเจน หน้าจอต้องใช้งานบนขนาดจอต่าง ๆ ผ่านแป้นพิมพ์ได้ มีจุดโฟกัสที่มองเห็น สีและข้อความอ่านได้ชัด และเคารพการตั้งค่าลดการเคลื่อนไหวของผู้ใช้

**AC-26 การตรวจรับก่อนส่งมอบ**  
แต่ละความสามารถต้องมีการทดสอบกรณีสำเร็จ กรณีข้อมูลผิด และกรณีไม่มีสิทธิ์ที่เกี่ยวข้อง Backend และ Frontend ต้องผ่านการตรวจสอบและทดสอบที่กำหนดในโปรเจกต์ โดยไม่แก้หรือลบการทดสอบเพียงเพื่อให้ผลผ่าน

## Error format (ทั้งระบบ)
{"error": {"code": "MACHINE_READABLE_CODE", "message": "human readable"}}

กรณี VALIDATION_ERROR เท่านั้น:
{"error":{"code":"VALIDATION_ERROR","message":"human readable","fieldErrors":[{"field":"field.path","message":"human readable"}]}}

## API Contract

ทุก Endpoint ที่ต้องยืนยันตัวตนใช้ Access Token และตรวจสิทธิ์ที่ Backend

```text
GET /health
    → 200 {"status":"ok"}

    → 503 SERVICE_UNAVAILABLE
```

### Authentication

วิธีออก Access Token จะกำหนดหลังจากเลือกระบบเข้าสู่ระบบของมหาวิทยาลัย

```text
GET /api/v1/auth/me
    → 200 User
    → 401 UNAUTHORIZED
    → 403 ACCOUNT_PENDING | ACCOUNT_SUSPENDED
    → 500 INTERNAL_ERROR

POST /api/v1/auth/logout
     → 204
     → 401 UNAUTHORIZED
     → 500 INTERNAL_ERROR
```

ทุกบทบาทดูรายการและรายละเอียดได้ การเพิ่ม แก้ไข ลบ และปรับความคืบหน้าอนุญาตเฉพาะ `COORDINATOR` และ `ADMIN`

```text
    → 500 INTERNAL_ERROR

     Content-Type: multipart/form-data

     Body: CreateResearchRequest และ contractFile

     → 201 Research
     → 401 UNAUTHORIZED
     → 403 FORBIDDEN | ACCOUNT_PENDING | ACCOUNT_SUSPENDED
     → 404 CONTINUATION_NOT_FOUND
     → 409 TITLE_ALREADY_EXISTS | CONTRACT_NUMBER_ALREADY_EXISTS
     → 413 PAYLOAD_TOO_LARGE
     → 415 UNSUPPORTED_MEDIA_TYPE
     → 422 VALIDATION_ERROR
     → 500 INTERNAL_ERROR

    → 200 Research

    → 403 FORBIDDEN

    → 422 VALIDATION_ERROR
```

## SQL
- หัวข้อนี้เป็นข้อกำหนด schema เป้าหมาย ไม่ใช่คำสั่งให้ล้างฐานข้อมูลหรือไฟล์ทุกครั้งที่เริ่ม server; migration และข้อมูลสำรองต้องจัดการแยกจาก runtime
- ตาราง `researches` ต้องมี `id`, `title`, `is_subsidized`, `project_type`, `research_kind`, `continuation_of_id`, `responsible_project_unit`, `responsible_budget_unit`, `start_date`, `end_date`, `budget_amount`, `thai_abstract`, `english_abstract`, `objectives`, `keywords`, `status` และ `process`
- `id` เป็น integer บวกที่ SQLite สร้าง เป็น primary key แบบไม่ใช้ค่าซ้ำหลังลบ และห้ามแก้ไข
- `continuation_of_id` เป็น nullable self-reference foreign key; ห้ามแก้ไข และใช้ `ON UPDATE RESTRICT` กับ `ON DELETE RESTRICT`
- ตาราง `research_members` เป็นความสัมพันธ์หนึ่งต่อหลายกับ `researches`; เก็บ `full_name`, `email`, `affiliation`, `contribution_percent` และ `role` แบบ `NOT NULL` โดย role อยู่ใน `LEAD`,`CO_RESEARCHER` และ percentage อยู่ใน `(0,100]` มีทศนิยมไม่เกิน 2 ตำแหน่ง
- ตาราง `research_contracts` เป็นหนึ่งต่อหนึ่งกับ `researches`; เก็บ `funding_type`, `funding_source_name`, `contract_number`, `storage_path`, `original_filename`, `content_type`, `size_bytes` และบังคับ `content_type='application/pdf'`, `size_bytes <= 20971520`
- เก็บ `contract_number_key` ที่ service สร้างด้วย Unicode trim และ case folding เป็น `NOT NULL UNIQUE` เพื่อบังคับเลขสัญญาทุนไม่ซ้ำภายใต้ concurrent writes; client ไม่รับหรือส่ง key นี้
- ข้อมูลข้อความใหม่เป็น `NOT NULL` และบังคับความยาว/อักขระตาม AC-04; `budget_amount > 0` และมี precision 2 ตำแหน่ง; วันจัดเก็บแบบ canonical ที่ตรวจสอบได้ แต่ API รับ/ตอบ `DD/MM/YYYY` ปี พ.ศ. และบังคับวันสิ้นสุดขั้นต่ำตาม AC-04
- `status` เป็น `NOT NULL` ค่าเริ่มต้น "กำลังดำเนินการ" และรับเฉพาะหกค่าที่ระบุใน AC-11
- `process` เป็น `NOT NULL` ค่าเริ่มต้น "สัญญาโครงการ" และรับเฉพาะแปดค่าที่ระบุใน AC-12
- constraint/index/trigger ต้องบังคับกฎ title ของงานต้นฉบับและงานต่อเนื่องให้ถูกต้องภายใต้ concurrent writes
- trigger ต้องห้ามแก้ `id` และ `continuation_of_id` หลังสร้าง
- trigger ต้องบังคับ status transition, process transition, terminal lock และการคง process เดิมเมื่อเข้าสู่ terminal status ตาม AC-11 และ AC-12
- ทุก connection ต้องเปิด foreign keys และทุก mutation ต้องทำใน transaction แบบ atomic; การเขียนไฟล์ใช้ staging และชื่อไฟล์ถาวรที่ระบบสร้าง ไม่ใช้ชื่อจาก client เป็น path
- PDF ต้อง parse ได้จนจบ มีอย่างน้อย 1 หน้า ไม่เสียหายและไม่เข้ารหัส/ป้องกันด้วยรหัสผ่าน; ไฟล์ที่ไม่ผ่านตอบ VALIDATION_ERROR ที่ `contractFile`
- วางไฟล์ใหม่ในตำแหน่งถาวรก่อน commit metadata; หาก transaction ล้มเหลวให้ลบไฟล์ใหม่ เมื่อ update สำเร็จจึงลบไฟล์เก่า และลบไฟล์ถาวรที่ไม่มี metadata อ้างอิงเมื่อเริ่ม server
- การลบใช้ staging เพื่อย้อนคืนไฟล์ได้ก่อน transaction commit; เมื่อเริ่ม server หาก staged deletion ยังมี metadata อ้างอิงให้คืนไฟล์ มิฉะนั้นให้ลบทิ้ง รวมทั้งล้าง upload staging ที่ค้าง เพื่อไม่ให้ crash ทิ้งข้อมูลอ้างไฟล์ที่หายหรือไฟล์กำพร้า
